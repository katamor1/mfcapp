# ADR 0008: アプリケーションをC++17に固定する

- **状態:** 承認済み
- **決定日:** 2026-07-24
- **決定者:** プロダクトオーナー指示
- **関連設計書:** `docs/superpowers/specs/2026-07-23-shelf-manager-architecture-design.md`
- **関連計画書:** `docs/superpowers/plans/2026-07-23-shelf-manager-mvp-foundation-fake-vertical-slice.md`

## 背景

対象となる配布環境および連携環境の制約により、テストと各アダプターを含むアプリケーション全体をC++17互換に保つ必要がある。初期実装では、アーキテクチャ上必須ではない複数のC++20言語機能および標準ライブラリ機能を使用していた。

機能要求は変更しない。GUIは引き続きワークを監視・操作し、外部の機械アクセスはApplication Portの背後に置く。したがって、言語バージョンの制約はアーキテクチャ変更ではなく、実装上の制約として扱う。

## 決定

1. すべてのプロジェクトを`/std:c++17`でコンパイルする。
2. MSVCで選択中の言語標準をコンパイル時に正しく確認できるよう、`/Zc:__cplusplus`を有効にする。
3. 共通Bootstrap Testを通じて、各テスト実行ファイルにC++17固定を検証するコンパイル時アサーションを含める。
4. C++20のdefaulted比較演算子および三方比較演算子を、C++17で使用できる明示的な比較演算子へ置き換える。
5. `std::jthread`および`std::stop_token`を、`std::thread`、atomicな停止フラグ、明示的な`join`へ置き換える。
6. `std::atomic<std::shared_ptr<T>>`を、`std::shared_ptr<T>`に対するC++17のatomic自由関数へ置き換える。
7. 一部ファイルだけをC++20でコンパイルする例外を設けない。C++17制約はDomain、Application、Infrastructure、Presentation、MFC、およびテストの全プロジェクトへ一律に適用する。
8. 本ADRが後続の承認済みADRで置き換えられない限り、新規コードおよび将来のCOMアダプターもC++17互換とする。

## 検討した代替案

### C++20を維持し、最新のVisual C++ Runtimeを前提にする

配布環境の制約を満たさないため採用しない。

### MFC実行ファイルだけをC++17にする

静的ライブラリとテストがC++20のABI、コンパイラー、保守上の依存を持ち続ける可能性があるため採用しない。

### 一部のソースファイルだけをC++20でコンパイルする

言語レベルが混在すると制約の検証が難しくなり、移行リスクが隠れたまま残るため採用しない。

## 結果

### 利点

- サポートするコンパイラー契約が明確になり、継続的に検証できる。
- CSVモックと将来のCOM Gatewayは、既存インターフェイスを通じて引き続き差し替え可能である。
- 単一プロジェクトからC++20専用依存が暗黙に入り込むことを防止できる。

### 欠点と制約

- 一部の比較演算子を明示的に記述する必要があり、定型コードが増える。
- スレッド停止とSnapshotのatomic公開は、新しい標準ライブラリのラッパーではなく、C++17互換の実装を記述する必要がある。

## 検証方法

- `Directory.Build.props`で`stdcpp17`および`/Zc:__cplusplus`を指定する。
- `BuildBootstrapTests.cpp`は、選択された言語レベルが厳密にC++17でなければコンパイルに失敗する。
- GitHub ActionsでDebug/Release × Win32/x64をビルドし、すべてのテストを実行する。
- ソース境界検査で、`<=>`、`std::jthread`、`std::stop_token`、`std::atomic<std::shared_ptr<...>>`の意図しない再導入を検出する。
