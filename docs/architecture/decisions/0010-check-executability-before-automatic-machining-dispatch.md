# ADR 0010: 自動運転開始時と加工場搬送直前に加工可否を判定する

- **状態:** 承認済み
- **決定日:** 2026-07-24
- **決定者:** プロダクトオーナー指示
- **関連設計:** `docs/superpowers/specs/2026-07-24-queue-priority-check-design-addendum.md`
- **関連計画:** `docs/superpowers/plans/2026-07-24-queue-priority-check-api-amendment.md`

## 背景

加工場管理システムは工具の所在と残寿命を管理しており、JSONをBSTRとして`comQueuePriorityCheckApi(input, output)`へ渡すことで、Workpieceごとの実行可否と工具状態を返す。

加工順位が高くても、必要な工具が存在しない、または工具寿命が不足するWorkpieceを加工場へ搬送すると、加工開始後の異常中断につながる。工具状態は加工の進行により変化するため、アプリケーション起動時の一回だけではなく、実際の搬送直前にも再確認する必要がある。

## 決定

1. 加工可否判定は自動運転開始時に実行する。
2. 加工可否判定は加工場への搬送要求を送る直前にも実行する。
3. 判定入力には、加工待ちキュー全体を現在の`QueuePriority`順で含める。
4. `Executable == "NG"`のWorkpieceをキュー末尾へ移動する。
5. OK群とNG群の内部では、判定前の相対順を維持する。
6. 並べ替え後は`QueuePriority`を1から連番で再採番する。
7. 順位変更は期待旧値を含む計画として書き込み、Standard読戻しで一致を確認する。
8. 搬送直前に旧候補がNGとなった場合、そのWorkpieceを搬送せず、順位調整後の先頭Workpieceを再選択する。
9. API失敗、不正JSON、Workpiece対応不整合、Snapshot競合、順位書込失敗、読戻し不一致では加工場へ搬送しない。
10. 外部APIは`IQueuePriorityCheckGateway`の背後へ置き、Application、Domain、Presenter、ViewへBSTRやJSON仕様を漏らさない。
11. C++17制約を維持する。

## JSON契約上の判断

- フィールド名は`Toolid`を含めて原表記を維持する。
- `Executable`は`OK`と`NG`を受け付ける。
- 工具`Status`は少なくとも`OK`、`End of Life`、`Not Found`を受け付ける。
- `Not Found`では`RemainLifeTime`が存在しない可能性があるため任意項目とする。
- `RemainLifeTime`は負値を許容する。
- 時間値の単位は未確定のため、整数の外部契約値として扱う。

## 検討した代替案

### 先頭Workpieceだけを判定する

採用しない。サンプルでは先行Workpieceの工具使用が後続Workpieceの残寿命へ影響しているように見えるため、現在のキュー順を含む全体判定が必要である。

### 自動運転開始時だけ判定する

採用しない。工具寿命や工具所在は運転中に変わるため、搬送直前の状態を保証できない。

### NG Workpieceの順位を一律に最大整数へ設定する

採用しない。順位の重複や欠番が生じ、既存の`MachiningQueue`不変条件を壊す。安定した区分け後に1から連番で再採番する。

### 工具`Status`をGUI側で独自解釈してExecutableを再計算する

採用しない。最終判定責務は加工場管理システムにあるため、順位調整にはWorkpiece単位の`Executable`を使用する。工具状態は説明・診断情報として保持する。

### API失敗時に前回の判定結果を使用する

採用しない。工具状態が変化している可能性があるため、古い判定で加工場へ搬送しない。

## 結果

### 利点

- 工具不足または寿命不足が判明しているWorkpieceを加工場へ送る可能性を下げられる。
- 自動運転開始時と実搬送直前で同じPolicyとUse Caseを再利用できる。
- NG Workpieceが複数存在しても順位が毎回入れ替わらない。
- 将来の正式COM実装とファイル駆動Mockを同じApplication Portの背後で差し替えられる。

### 欠点と制約

- 自動運転開始と搬送Dispatchに外部API待ち時間が追加される。
- API停止時は安全側に倒すため、加工場への搬送が停止する。
- Workpiece全体の工具使用計画を構築する処理が必要になる。
- APIの計算規則が未確定な部分は、正式仕様受領後に契約テストを更新する必要がある。

## 検証方法

- 添付サンプルJSONを回帰フィクスチャとして使用する。
- OK／NGを安定して区分けするDomainテストを実行する。
- 欠落、重複、余分なWorkpieceを拒否する契約テストを実行する。
- 自動運転開始時と搬送直前の二つのTriggerから同じUse Caseが呼ばれることをテストする。
- 順位書込後の読戻し一致をテストする。
- 旧候補がNGとなった場合に搬送Gatewayが呼ばれないことをテストする。
- Debug/Release × Win32/x64でビルドと全テストを実行する。
