# ADR 0009: 設計書・計画書の説明文は日本語を標準とする

- **状態:** 承認済み
- **決定日:** 2026-07-24
- **決定者:** プロダクトオーナー指示
- **対象:** 設計書、実装計画書、計画追補、ADR、受入チェックリスト

## 背景

本プロジェクトの設計者および主要レビュアーは日本人を想定している。設計判断、失敗時の動作、実装順序、受入条件が英語と日本語で混在すると、レビュー時の読み替えが増え、重要な条件の見落としや解釈差が生じやすい。

一方、クラス名、関数名、ファイル名、コマンド、API名、外部仕様の値などを無理に日本語化すると、実装との対応関係が分かりにくくなる。そのため、説明文の標準言語と技術識別子の表記を分けて扱う必要がある。

## 決定

1. 設計意図、背景、判断理由、手順、受入条件、制約、リスクなど、内容を説明する文章は日本語を標準とする。
2. 文書タイトル、章見出し、表の説明列、注記も原則として日本語で記述する。
3. クラス名、関数名、型名、名前空間、ファイル名、ディレクトリ、コマンド、オプション、API名、データ値、エラーコードは原表記を維持する。
4. 英語の技術用語を使用する場合は、日本語の文脈から役割と判断内容を追跡できるようにする。
5. 外部資料の引用を原文で残す必要がある場合は、必要に応じて日本語の要約または説明を併記する。
6. ソースコード内の識別子、ログ出力、プロトコル値、ベンダー契約の言語は、本ADRの対象外とする。
7. 新規文書だけでなく、作業中の設計書、計画書、ADRに英語の説明文が残っている場合も、意味を変えずに日本語へ改訂する。

## 検討した代替案

### 文書全体を英語に統一する

主要レビュアーの確認負荷が増え、レビュー速度と解釈の一貫性を損なうため採用しない。

### 日本語と英語を同量で併記する

文書量がほぼ倍になり、更新漏れによって二つの記述が不一致になる可能性があるため、通常の設計書・計画書では採用しない。

### 各作成者の判断に任せる

文書間の表記が再び混在し、プロジェクト全体でのレビュー基準が安定しないため採用しない。

## 結果

### 利点

- 設計判断と受入条件を、日本語話者のレビュアーが直接確認できる。
- 実装との対応に必要な技術識別子は原表記のまま追跡できる。
- 文書ごとの言語選択に関する迷いを減らせる。

### 欠点と制約

- 外部の英語資料を参照する場合、要約または訳語の整備が必要になる。
- 国際的な共有が必要になった場合は、別途英語版または翻訳工程を用意する必要がある。

## 検証方法

- 設計レビューおよびPRレビューで、説明文が日本語を標準としていることを確認する。
- コード識別子、ファイル名、コマンドなどの原表記を不用意に翻訳していないことを確認する。
- 設計書、主計画書、計画追補、既存ADRの改訂時に本ADRへの適合を確認する。
