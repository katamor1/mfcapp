| 項目 | 内容 |

| 文書状態 | 承認済み |

| 対象 | 自社管理の製品コード、テストコード、Fake／Mock／Adapter、ビルド・検査スクリプト |

## 1. 目的

本ポリシーは、コメント量を増やすための規則ではない。設計者とレビュー者が、コードから直接は読み取れない次の情報を正確に追跡できるようにすることを目的とする。

- なぜその設計、分岐、処理順序、失敗動作を採用したか
- 安全上、どの条件で処理を実行または中止するか
- どのスレッドから呼び出せるか、どの順序で停止・破棄するか
- ポインタ、BSTR、COMオブジェクト、ハンドル等を誰が所有・解放するか
- COM、JSON、CSV、ベンダー仕様、ADR等のどの契約を根拠にしているか
- 暫定実装がどの課題と完了条件に結び付いているか

本アプリケーションは、加工順位に基づく自動搬送、加工完了または異常中断後の戻し搬送、加工可否判定に伴う順位変更などを扱う。したがって、コメントは特に安全判断と外部契約のレビュー証跡として使用する。

---

## 2. 基本原則

### 2.1 コードで表現できることはコードで表現する

適切な型、関数名、クラス分割、インターフェイス、テストによって意図を表現し、コメントを設計不足の代替にしない。

### 2.2 コメントにはコードから読み取れない情報を書く

処理の逐語説明ではなく、理由、制約、前提、安全性、所有権、外部仕様との対応を記述する。

### 2.3 コメントはコードと同じ品質管理対象とする

コードと矛盾するコメントは不具合として扱う。関連コードを変更するPRでは、コメントも同じPRで更新または削除する。

### 2.4 コメント率や行数を品質指標にしない

コメントの有無ではなく、レビューに必要な判断根拠を追跡できることを重視する。コメント率、日本語文字率、タグ数等の数値目標は設けない。

### 2.5 詳細な設計判断は適切な文書へ置く

局所的な理由はソースコメントに記載する。背景、代替案、長期的な影響まで必要な判断はADRまたは設計書へ記録し、ソース側から参照する。

## 3. 適用範囲

### 3.1 適用対象

- 自社管理の製品コード
- 自社管理のテストコード
- Fake、Mock、Stub、Adapter
- PowerShell等のビルド、検査、補助スクリプト
- 自社管理の設定・補助コード
- ベンダー提供コードへ自社が追記または変更した部分

### 3.2 適用除外

- 自動生成コード
- 外部ライブラリの原文
- 未変更のベンダー提供コード
- ビルド時に生成される中間ファイル
- `vcpkg_installed/`、`out/`、`obj/`等の生成ディレクトリ

外部コードをコピーして自社管理下へ取り込んだ場合は、原則として適用対象へ移る。

## 4. コメント言語

説明文は日本語を標準とする。次の名称は、実装および外部契約との対応を保つため原表記を維持する。

- クラス名、関数名、型名、名前空間
- API名、COM名、BSTR等の技術識別子
- ファイル名、パス、コマンド、オプション
- JSONフィールド名、CSV列名、プロトコル値
- エラーコード、列挙値
- `Workpiece`、`QueuePriority`、`MachineSnapshot`等のコード上の用語

例:

```cpp
// SAFETY: ExecutableがNGのWorkpieceは加工場へ搬送せず、
// QueuePriorityの末尾グループへ移動する。
```

コード識別子を無理に日本語化せず、日本語の文脈から役割と判断内容を追跡できるようにする。

---

## 5. コメントを必須とする箇所

次に該当する場合、形式を問わず必要な情報をコメントで補う。

1. Public API
2. Fail Closed、操作禁止、再試行禁止等の安全判断
3. スレッドアフィニティ、同期条件、再入可否、呼出し順序、終了順序
4. ポインタ、BSTR、COMオブジェクト、ハンドル等の所有権・寿命・解放責任
5. COM、JSON、CSV、ベンダーAPI等の外部契約
6. コードだけでは理由を誤解しやすい非自明な判断
7. 正式仕様が未確定な暫定実装と、その安全側の動作

明白なgetter、単純な値変換、名前と構造だけで十分に読める処理にはコメントを要求しない。

## 6. コメントの記述ルール

### 6.1 記述する内容

| 観点 | 記述内容 |
|---|---|
| 設計理由 | なぜその方式、順序、データ構造を選んだか |
| 制約 | 外部API、C++17、MFC、COM、性能等による制限 |
| 安全性 | Fail Closed、実行禁止条件、非再試行、読戻し確認の理由 |
| スレッド | 呼出し可能スレッド、排他条件、再入可否、終了順序 |
| 所有権 | 誰が生成、保持、解放するか、参照の有効期間 |
| 外部契約 | COM仕様、JSONフィールド、CSV形式、要求、ADRとの対応 |
| 暫定対応 | 正式仕様が未確定であること、安全側の仮動作、置換条件 |
| 非自明な期待 | 一見すると不自然だが意図的な動作、値、順序 |

### 6.2 記述しない内容

コードを日本語へ逐語変換するだけのコメントは書かない。

悪い例:

```cpp
// Workpieceをループする。
for (const auto& workpiece : workpieces) {
```

```cpp
// QueuePriorityを1増やす。
++queuePriority;
```

このようなコメントが必要になる場合は、変数名、関数分割、型設計を先に見直す。

### 6.3 コメントの位置

コメントは原則として対象コードの直前に置く。

```cpp
// SAFETY: 判定後にSnapshotVersionが変化している場合、
// 古い加工可否結果を現在のキューへ適用しない。
if (currentVersion != checkedVersion) {
    return Result<void>::Failure(
        {ErrorCode::Conflict, "Snapshot version changed."});
}
```

複数の関数やクラスに共通する判断は、同じ長文を各所へ複製せず、ADRまたは設計書へ記録する。

### 6.4 コメントの長さ

局所コメントは、原則として数行で要点を説明する。背景、代替案、長期影響まで必要な場合はADRへ移し、ソース側は参照と局所的な結論だけを記載する。

## 7. 標準コメントタグ

タグは重要な判断点でのみ使用する。タグを付けること自体を目的にしない。

### 7.1 `WHY:`

実装理由、採用したトレードオフ、直感に反する処理を説明する。

```cpp
// WHY: NG Workpiece同士の相対順を維持し、
// 判定のたびに末尾グループ内の順序が変動することを防ぐ。
std::stable_partition(...);
```

### 7.2 `THREAD:`

スレッドアフィニティ、同期条件、再入可否、停止・破棄順序を説明する。

```cpp
// THREAD: COMを初期化した専用STAスレッドからのみ呼び出す。
// UIスレッドからの直接呼出しは禁止する。
HRESULT ComApiClient::Get(...);
```

### 7.3 `SAFETY:`

Fail Closed、非冪等処理、再試行禁止、操作抑止の理由を説明する。

```cpp
// SAFETY: 搬送要求は非冪等であるため、
// 応答が不明な場合も自動再試行しない。
return transportGateway_.RequestTransport(request);
```

### 7.4 `SOURCE:`

要求、外部仕様、ADR、Issue、契約フィクスチャ等の判断根拠を示す。

```cpp
// SOURCE: config/mock/queue-priority-check/output.json。
// 外部契約に合わせ、フィールド名Toolidの大文字・小文字を変更しない。
json["Toolid"] = tool.toolId;
```

### 7.5 タグの使い過ぎを避ける

一つのコメントへ複数タグを機械的に並べない。主目的となるタグを一つ選び、必要な補足を本文へ含める。複数の独立した重要事項が集中している場合は、クラスまたは関数の責務が過大でないかも確認する。

## 8. Public APIのドキュメントコメント

### 8.1 形式

`//`、`///`、`/** ... */`のいずれも使用可能とし、形式は統一しない。レビューでは、利用側が実装内部を読まずに正しく安全に呼び出せるかを確認する。

### 8.2 Public APIの範囲

- 別プロジェクトまたは別レイヤーから使用されるクラス・関数
- Application Port等の抽象インターフェイス
- PresenterまたはOrchestratorから呼び出すUse Case
- Infrastructureが実装するGateway／Adapterインターフェイス
- 複数機能から共有されるDomain型・Policy
- 別コンポーネントから使用されるMFC公開メソッド
- テスト用Fake／Mockの公開設定インターフェイス

同一`.cpp`内だけで使用する内部関数や、名前と型だけで意味が明確な単純アクセサーは対象外にできる。

### 8.3 記載項目

該当する項目だけを記載する。該当しない情報を定型的に「なし」と並べる必要はない。

| 項目 | 記載する内容 |
|---|---|
| 責務 | 何を行うAPIか、何を行わないAPIか |
| 前提条件 | 呼出し前に成立している必要がある状態 |
| 引数 | 意味、単位、許容範囲、並び順、null可否 |
| 戻り値 | 成功時に何が保証されるか |
| エラー | 主な失敗条件、失敗時に変更が残る可能性 |
| 副作用 | COM書込み、Snapshot更新、ファイル読込み、通知等 |
| スレッド | 呼出し可能スレッド、同期／非同期、再入可否 |
| 所有権 | ポインタ、BSTR、参照、ハンドル等の所有・解放責任 |
| タイムアウト | 待機上限、取消可否 |
| 再試行 | 自動再試行の有無、呼出し側の再試行可否 |
| 外部契約 | COM、JSON、CSV、ADR等の根拠 |

### 8.4 成功の意味を明確にする

外部システム操作では、次を区別する。

- 要求を受け付けた
- 書込みAPIが成功した
- 読戻し値が一致した
- 物理搬送が開始した
- 物理搬送が完了した

悪い例:

```cpp
// 搬送に成功する。
Result<TransportReceipt> RequestTransport(...);
```

良い例:

```cpp
// 搬送要求を一度送信する。
// 成功戻り値は要求受付を示し、物理搬送完了は保証しない。
// 完了判定は後続の状態読戻しで行う。
Result<TransportReceipt> RequestTransport(...);
```

### 8.5 所有権を伴うAPI

BSTR、ポインタ、COMオブジェクト、Windowsハンドルを扱うPublic APIでは、所有権を必ず明記する。正式仕様が未確定の場合も、未確定であることと現時点での安全な閉じ込め方を記載する。

```cpp
// inputの所有権は呼出し側に残る。
// outputの割当・解放責任は正式なベンダー契約受領後に確定する。
// SAFETY: 所有権契約が確定するまで、このRaw APIを
// ApplicationまたはPresentationから直接呼び出さない。
virtual HRESULT Check(BSTR input, BSTR* output) = 0;
```

### 8.6 オーバーライド実装側

抽象インターフェイス側ですでに契約を説明している場合、実装クラスで同じ文章を複製しない。Adapter固有の変換、制約、再現範囲だけを記載する。

```cpp
// output.jsonのJSON構造とBSTR受渡しだけを再現する開発用Adapter。
// COM apartment、通信遅延、ベンダーHRESULT、取消動作は再現しない。
class FileBackedQueuePriorityCheckApi final {
```

## 9. `TODO`の運用

### 9.1 必須情報

`TODO`には、次を必須とする。

1. 追跡可能な課題番号
2. 検証可能な完了条件

```cpp
// TODO(#123): 正式なCOMデータ辞書を受領後、
// 暫定dataIdを本番用MachineDataCatalogへ置き換える。
// 完了条件: 正式IDとのAdapter契約テストがWin32/x64で成功すること。
```

禁止例:

```cpp
// TODO: あとで対応する。
```

```cpp
// TODO(#123): 改善する。
```

### 9.2 マージ後に残せる条件

次をすべて満たす場合に限り、`TODO`をマージ後のコードへ残せる。

- 現在の機能が安全に成立している
- 未対応部分がFail Closedまたは明示的な未対応状態になる
- 後続課題が登録済みである
- 対応しなくても誤った成功状態にならない
- 完了条件が検証可能である

### 9.3 残してはいけない条件

次に該当する場合、`TODO`を付けてもマージ不可とする。

- 現在の処理が安全条件を満たさない
- データ破損、二重搬送、未定義動作、リソースリークの可能性がある
- 成功・失敗を誤って表示する
- PRの受入条件を満たしていない
- 現在の不具合をIssue化だけで先送りしている

## 10. `FIXME`の運用

`FIXME`は、現在のコードに既知の不具合、仕様違反、安全上の問題、誤動作の可能性があることを示す。原則としてマージ前に解消する。

やむを得ず短期間残す場合は、次をすべて記載する。

- 課題番号
- 影響範囲
- 暫定的に安全を保つ方法
- 完了条件

```cpp
// FIXME(#245): comQueuePriorityCheckApiの正式なtimeout契約が未確定。
// 影響: API応答不能時の待機上限を正式値で保証できない。
// SAFETY: timeoutまたは応答不明時は、順位変更と加工場搬送を確定しない。
// 完了条件: ベンダー仕様値を反映し、timeoutと取消可否の契約テストを追加する。
```

例外的に残す場合は、影響範囲が限定され、本番動作へ到達しないか安全側に停止し、回避策とリリース前の解消管理が存在することをレビュー者が確認する。

判断に迷う場合、現在のコードが受入条件を満たし安全に動作するなら`TODO`、満たさないなら`FIXME`として扱う。

## 11. コメントアウトされた無効化コード

### 11.1 原則禁止

コミット済みコードへ、コメントアウトした旧実装、試行コード、デバッグ分岐を残さない。不要なコードは削除し、必要ならGit履歴から参照する。

```cpp
// oldGateway.Apply(plan);  // 禁止
```

`#if 0`も同じ扱いとする。

### 11.2 短期例外

障害調査、ベンダー環境での比較、段階的切替等で一時的に残す必要がある場合は、次を必須とする。

- 課題番号
- 無効化理由
- 現在の実行経路
- 復旧または削除条件

```cpp
// 一時無効化(#432):
// COMベンダー環境で通信断後の再接続を比較調査するため、
// legacyReconnectは呼び出さない。
// 現在の実行経路: ReconnectCoordinator::Execute。
// 削除条件: #432完了時にlegacyReconnectと本コメントを削除する。
// const auto result = legacyReconnect();
```

正式な切替機能は、コメントアウトではなくApplication Port、Adapter、Strategy、Feature Flag、設定値、Dependency Injection等で実現する。

### 11.3 履歴保存目的のコメントは禁止

変更履歴はGit、PR、Issue、ADRで管理する。日付付きの変更履歴や旧実装の説明をソースへ残さない。

過去障害から導かれた現在の安全条件は、履歴ではなく現在の設計理由として記載できる。

## 12. テストコード内のコメント

### 12.1 基本方針

テスト名、Fixture、ヘルパー関数、変数名で意図を表現することを優先する。通常のArrange／Act／Assertを説明するだけのコメントは付けない。

### 12.2 コメントが必要な場合

- 境界値の根拠が外部仕様または安全条件に由来する
- 過去障害の再現条件がコードだけでは分からない
- 一見すると誤りに見える期待値を意図的に採用している
- 時刻、スレッド、非同期順序に特別な前提がある
- Fake／Mockの再現範囲と非再現範囲を明確にする必要がある
- Fail Closed、非再試行等の安全側の期待結果を説明する必要がある

例:

```cpp
// SAFETY: 搬送要求の応答が不明でも自動再送しない。
// 同一Workpieceへの二重搬送要求を防ぐため、呼出し回数は1回のままとする。
EXPECT_EQ(1, gateway.TransportRequestCount());
```

```cpp
// WHY: NG Workpiece同士の相対順を維持する。
// 判定のたびに末尾グループ内の順位が揺れることを防ぐ回帰テスト。
EXPECT_EQ(expectedOrder, outcome.orderedWorkpieceIds);
```

### 12.3 Arrange／Act／Assertコメント

機械的な区切りコメントは原則として使用しない。区切りがないと読みにくい場合は、テスト分割、Fixture、Builder、ヘルパー関数、変数名の改善を先に検討する。

長いシナリオ試験で段階が業務上の意味を持つ場合は、業務シーケンスを示す節コメントを許容する。

### 12.4 テストデータ

JSONは標準仕様上コメントを持たないため、疑似コメントを追加しない。説明はテスト名、テストコード、`docs/testing/`、Fixture用README、JSON Schemaの`description`へ記載する。

CSV内コメントは、ローダーが正式に許容する場合だけ使用する。

## 13. コメントの保守責任

コードと矛盾するコメントは、コード不具合と同等に扱う。関連コードを変更するPRでは、コメントも更新または削除する。

次は古いコメントとして扱う。

- 変更済みの引数、戻り値、単位、エラー条件を説明している
- 現在は存在しないクラス、関数、仕様を参照している
- 解消済みの制約や暫定対応を説明している
- 実際には行われない再試行、排他、読戻し確認を行うと記載している
- `SOURCE`で参照した仕様、ADR、Issueが現在の実装根拠と一致しない
- Fake／Mockが実際より広い範囲を再現すると誤認させる

コメントが不要になった場合は、無理に別の文章へ置き換えず削除する。

## 14. レビュー判定

### 14.1 マージをブロックする違反

次は、原則として修正されるまでマージ不可とする。

- 安全性に関わる判断の根拠が不足または実装と矛盾している
- スレッド制約、再入可否、同期条件、終了順序が不明確である
- BSTR、ポインタ、COMオブジェクト、ハンドル等の所有権・解放責任が不明確である
- COM、JSON、CSV、外部API等の契約根拠が不明確である
- Public APIの前提条件、成功保証、副作用、失敗条件が不足している
- 課題番号または完了条件のない`TODO`
- 例外条件を満たさず残された`FIXME`
- 説明なしのコメントアウトコードまたは`#if 0`
- コードと矛盾する安全コメント、スレッドコメント、所有権コメント、外部契約コメント

### 14.2 改善指摘として扱える違反

意味が正しく、安全判断にも影響しない場合、次は非ブロッキングの改善指摘にできる。

- コメントがやや冗長である
- 日本語として読みづらい
- コメント位置が対象コードから離れている
- タグを使うと読みやすいが、タグなしでも意味は明確である
- テスト名とコメントが多少重複している
- 識別子から十分読める内容を重複している
- 長文をADRへ移した方が保守しやすい

誤読によって安全条件や外部契約の判断を誤る可能性がある場合は、ブロッキングへ引き上げる。

---

## 15. 人手レビュー用チェックリスト

```text
[ ] コメントは処理の逐語説明ではなく、理由・制約・根拠を示している
[ ] 安全上の実行条件と中止条件を追跡できる
[ ] 非冪等処理の再試行可否が明確である
[ ] スレッドアフィニティ、同期、再入、終了順序が明確である
[ ] BSTR、ポインタ、ハンドル等の所有権と寿命が明確である
[ ] Public APIの前提条件、成功保証、副作用、失敗条件が明確である
[ ] COM、JSON、CSV等の外部契約に根拠がある
[ ] 暫定仕様と正式仕様を区別している
[ ] TODOに課題番号と検証可能な完了条件がある
[ ] FIXMEを残す例外条件が満たされている
[ ] コメントアウトコードやデバッグ用コードが残っていない
[ ] テストコメントが期待値の理由や契約を補足している
[ ] コードとコメントが矛盾していない
[ ] 関連コードの変更に合わせてコメントも更新または削除されている
```

レビュー指摘では、単に「コメントを追加してください」とせず、欠けている判断情報を具体的に示す。

良い指摘例:

> このAPIの成功戻り値が搬送要求の受付だけを意味するのか、状態読戻しまで確認済みなのか判断できません。Public APIコメントに成功保証の範囲を記載してください。

> `output`のBSTRを誰が解放するか不明です。正式仕様が未確定であれば、未確定であることと、現在どのAdapter内に所有権を閉じ込めているかを記載してください。

## 16. CIによる軽量検査

### 16.1 役割分担

```text
CI:
  形式的な違反と取り忘れを検出する

人手レビュー:
  判断理由、安全性、契約、コードとの整合性を確認する
```

CI合格を、コメント内容が妥当であることの保証にはしない。

### 16.2 初期適用単位

段階導入の初期段階では、PRで追加または変更された自社管理ファイルについて、変更行だけでなくファイル全体を検査する。

変更していない既存ファイルの違反は、当該PRを自動的にはブロックしない。人手レビューで重大な矛盾を発見した場合はIssue化し、現在の変更と一体で誤判断を招く場合は同じPRで修正する。

### 16.3 機械検出対象

- 課題番号を伴わない`TODO`
- 課題番号を伴わない`FIXME`
- `TODO`近傍に完了条件がない
- `FIXME`近傍に影響、安全策、完了条件がない
- `#if 0`
- 明らかなコメントアウトコード
- 標準タグ`WHY`、`THREAD`、`SAFETY`、`SOURCE`の明らかな綴り違い
- 典型的なデバッグ用の強制成功、固定認証、旧実装無効化コメント

### 16.4 CIで判定しない項目

- コメントの理由が本当に妥当か
- `SAFETY`の内容が実装と一致するか
- Public APIの説明が十分か
- コメントが逐語説明か
- 日本語として自然か
- `SOURCE`が実装根拠として適切か
- コメントが必要な非自明箇所を網羅しているか
- Fake／Mockの再現範囲が正確か

### 16.5 対象拡張子と除外

初期検査対象は、自社管理の次の拡張子を基本とする。

```text
.h
.hpp
.cpp
.cxx
.ps1
```

必要に応じてCMake、MSBuild、設定スクリプト用拡張子を追加する。

次のディレクトリは除外する。

```text
vcpkg_installed/
out/
obj/
packages/
third_party/
external/
generated/
```

### 16.6 誤検出への対応

ソース中へ安易な抑止コメントを追加しない。次の順で対応する。

1. 検査ロジックを修正する
2. 対象拡張子または除外ディレクトリを調整する
3. 外部コード・自動生成コードとして明示的に除外する
4. 必要な場合だけ、Issue番号、理由、削除条件を伴う限定的な許可リストを使用する

## 17. 段階導入

### 17.1 高リスク領域の整備順序

1. 外部境界
   - `comQueuePriorityCheckApi`
   - BSTR所有権
   - COM API
   - JSON／CSV Codec
   - 暫定IDと正式契約の区別
2. 安全上の変更処理
   - 自動運転開始
   - 加工場への搬送直前判定
   - `QueuePriority`変更
   - 手動搬送
   - 書込み後の読戻し確認
   - 非冪等操作の再試行禁止
3. スレッドとライフサイクル
   - COM専用STAスレッド
   - Monitoring Worker
   - Operation Executor
   - 停止、join、依存オブジェクト破棄の順序
4. Public API
   - Application Port
   - Use Case
   - Gateway
   - Domain Policy
5. Fake／Mock
   - 再現する契約
   - 再現しない実機特性
6. テスト
   - 境界値の根拠
   - Fail Closedの期待結果
   - 過去障害の再現条件
   - スレッド・時刻依存の前提
7. その他の非自明な判断

### 17.2 新規コード

本ポリシー承認後に追加する新規ファイルは、作成時点から全面適用する。新規ファイルには「既存コードであること」を理由とした例外を認めない。

### 17.3 全ファイル検査への移行条件

次を満たした時点で、変更ファイル単位の検査からリポジトリ全体の検査へ移行する。

- 高リスク領域の整備が完了している
- 自社管理コードに既知の機械検出違反がない
- 外部コード・自動生成コードの除外規則が確定している
- CI実行時間と誤検出数が運用可能である
- PRレビュー項目と検査規則が対応している

移行は別PRで行い、検査結果と規則変更をレビュー可能にする。

コメントポリシー導入の初期完了条件を次とする。

